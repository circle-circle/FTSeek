## 2. 架构 (重构后)

```
app/push/
├── __init__.py          (26 行) 公开 API
├── message.py          (153 行) PushMessage + Level/Category enum + 4 helper
├── channels.py         (121 行) Channel ABC + DingTalk/Feishu/FlagFile 3 个 wrapper
├── aggregator.py       (161 行) 5min 窗口聚合 + 自动摘要
├── dedup.py             (35 行) 1min 同 key 去重
├── health.py            (90 行) 每小时 ping + 失败计数
└── hub.py              (208 行) PushHub 主入口 (单例)
```

### 推送流程

```
caller → hub.push(msg)
   ↓
1. dedup_key 60s 检查 → 命中? 跳过 (deduped++)
   ↓
2. is_aggregable? (LOW + aggregate_key) → 入桶 (aggregated++)
   ↓
3. 立即发送:
   - 排序 channels by priority
   - CRITICAL → 全通道广播
   - 其他 → 主通道优先, 失败 fallback 次通道
   - HIGH/CRITICAL 全失败 → flag 文件兜底
```

### Channel 优先级 (默认)

| Channel | Priority | 用途 |
|---------|:---:|------|
| `DingTalkChannel` | 1 (主) | 大部分推送 |
| `FeishuChannel` | 2 (备) | DingTalk 失败时自动 fallback |
| `FlagFileChannel` | 99 (兜底) | 仅 HIGH/CRITICAL 且主备都失败时写 `critical_alerts.flag` |

## 3. 关键设计决策

### 3.1 不删旧代码 (向后兼容)
- `app/notifier/{feishu,dingtalk}.py` 完全保留 — `Channel` wrap 它们.
- 旧调用 `scheduler.notifier.notify_order_filled(...)` 继续工作.
- 新增 PushHub 是**并行**链路 (双路过渡期), `order_executor._notify_order` 同时进两条.

**收益**: 1 周双路后 daily_review 验证 PushHub 数据无丢失, 再删旧路径.

### 3.2 聚合策略 (按用户选 "推荐: 交易类 5min + 告警立即")
- LOW (单笔成交/小亏平仓) → 5min 窗口聚合, 自动生成"交易聚合 (3 开 5 平, +$210)" 摘要
- NORMAL (大盈亏 $500+, 计划生成) → 立即推送 (不聚合)
- HIGH/CRITICAL (风控/熔断) → 立即推送 + 多通道广播 + flag 兜底

**5/15 重复推送压力测试**:
- 旧: 23:04-23:07 SNDK 5 条独立 (用户被骚扰)
- 新: 这 5 条都是 LOW, 进入 5min 桶, 23:08 输出 1 条聚合 ("3 开 2 平, -$65")

### 3.3 防疲劳 (按用户选 "推荐: 多通道 fallback + 每小时 ping")
- **DedupCache**: 60s 同 key 跳过 (例: 同 trace_id 重复触发)
- **HealthMonitor**: 每小时 ping (Level.INFO 隐式消息), 失败 3 次告警
- **聚合**: 已隐含防疲劳 (5 条 → 1 条)

**未启用 AlertDebouncer 升级机制**: 简单 dedup 足够覆盖, 升级机制等 30+ 案例数据再评估.

### 3.4 渐进迁移 (不一次性切流量)
| 阶段 | 状态 | 已迁移 |
|-----|---|----|
| 1 | ✅ 本次 | `_notify_order` / `_notify_exit` 双路 |
| 1 | ✅ 本次 | `send_critical` 双路 (PushHub + 旧重试) |
| 2 | ⏸ 等数据 | premarket_planner / open_checker / scheduler_triggers 复盘推送 |
| 3 | ⏸ 等评估 | 删除 `observability/feishu_client+feishu_bot+feishu_alert` (3 个重复) |
| 4 | ⏸ 等数据 | `app/notifier/*` 改为只为 `Channel` 服务的 backend |

## 9. 多想一步

### 为什么不用 publish-subscribe?
**考虑过**: kafka/redis pubsub 解耦更优雅.
**结论**: 单进程内不值得. 直接函数调用 + 后台线程 (聚合/健康) 已够, 加 broker 是 over-engineering.

### 为什么不实施 LLM 自动摘要?
**考虑过**: 5min 窗口用 LLM 生成"3 笔交易主导是 ARM SHORT, 触发 vwap/bollinger 信号..."
**结论**: 用户答案选了 "推荐方案" 而非"激进+LLM". 当前规则模板已足以传达信息, LLM 成本+延迟 ROI 低.
等用户实际看到聚合摘要不满意, 再升级到 LLM.

### 为什么 dedup TTL 是 60s, 不是 5min?
**考虑过**: 5min 等价于聚合窗口, 看似一致.
**结论**: dedup 是防"同事件重复触发" (例: 同 trace_id 多次回调), 60s 已够防误触发; 聚合是防"短时多事件骚扰", 5min 才合理. 两者目的不同, 时长应分.
