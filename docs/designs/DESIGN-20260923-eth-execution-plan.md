# 设计草案：ETH 执行计划（Execution Plan）— 从「盲扫-发现」到「计划-消费」

- **日期**：2026-09-23 | **状态**：**设计阶段（未落地、未改一行代码）**
- **触发**：用户提案 —— "各公司财报日是固定的，当日的通过循环拉取并不合理，是否可以类似通过 DA 或者 UE 模式生成盘前/盘后的执行计划"
- **本文性质**：设计树（自问自答）+ 底牌清单 + 模块线索 + 历史坑映射 + 行动方案；**等逻辑清晰并经用户拍板后**才进 RFC/落地
- **非目标（先钉死）**：退出链（`extended_hours_exit_cron`、SL/TP、孤儿单、EOD）**一行不动**；RTH 钱链（`app/playbook/*`、`playbook_instructions`）**不动**；本设计只改"入场侧的**人群发现方式**"

---

## 0. 一句话结论

**用户命题成立，但收益不是"多出单"**：事件人群是**日历预先已知**的集合（实测窗口 T-2…T+6、36/40 行带相位），当天靠 5 分钟循环把它"发现"出来是最弱的一环（实测每轮 37–40 只榜单票对事件人群贡献 **0**；9/22 那天因为还没有日历源，事件票 **100%** 靠榜单撞上）。计划化换来的是 **可见性 + 去无用功 + 语义正确**，换来不了出单 —— 出单卡在量闸/价差/actual 迟到（RFC-102/103 已分别处理与量化）。

## 2. 设计树自问自答（核心；Q→A→对设计的影响）

### Q1 —— 事件人群能不能**提前枚举**？
**能。** B1+B2：日历窗口已含 T-2…T+6、90% 带相位；今日 9/24 的 8 行（7 带相位）现在就在手上。
⇒ **设计影响**：计划可以在 **T-1 晚间**生成，不必等当天。

### Q2 —— 计划里要不要 LLM（像 DA/UE 那样）？
**不要（初版）。** 三个理由：① 现行 ETH 链是**规则链**（判据①②③ + 分档量闸 + 价差/深度），引入 LLM 会新增一个**不可复算**的失败面；② UE 用 LLM 是因为它要回答"**没有事件也能不能做**"（宇宙扩张），而我们这条链的**硬约束就是"必须有事件"**，属于可枚举问题，规则足够；③ 你的目标是"战胜费用线/降亏"，这要求每笔可回溯到规则与数字。
⇒ **设计影响**：计划 = **规则生成的观察名单 + 状态机 + 门槛快照**，**不含方向判断、不含 entry_zone/SL/TP**（那仍由下单时的门链与费用模型算）。若将来要加 LLM 排序，作为**独立影子**，不进判定。

### Q3 —— 计划放哪里？（**本设计最大的分叉**）
三个选项：
- **甲：复用 `playbook_instructions`**，加 `session` 维度。优点：一张真源、复用 `execution_state/attempt/broker_order_id` 生命周期与报表。缺点：那是 **RTH 钱链**（`app/playbook/*` 纯 RTH，实测 A3），加维度 = 改钱链 schema + 消费者 + 全部回归面；且 ETH 的门与 RTH 完全不同 ⇒ 计划卡字段大半不适用，反而要加一堆 `NULL` 列。
- **乙：新表**（如 `ext_hours_plans`）。优点：生命周期语义可照抄 UE 的（`PENDING/attempt/broker_order_id`）。缺点：**第二份真源** ⇒ 与 `playbook_instructions` 的"谁是真"问题会长期存在。
- **丙（推荐）：文件工件 + 影子入库**：`data/loops/ext_entry_plan/<et_date>_<session>.json`（计划卡数组）+ 幂等键 `(et_date, symbol, session, phase)`；执行器**只读**；先以 `jsonl` 台账落"计划 vs 实际"对账，**不建表**。等形态稳定（跨日读数证明字段够用）再决定是否入库/入表。
⇒ **设计影响**：**零碰钱链**（甲/乙都要动钱链或造第二真源）；符合"先可见再打磨"；RFC-101 的教训（先造设施、收益为 0 再回滚）在这里被主动规避 —— 先用**最小载体**验证"计划"这个抽象有没有用。

### Q4 —— 谁生成、什么时候生成？（**计划的新鲜度**是核心风险）
- **盘前计划**：**T-1 20:30 ET 生成（用窗口数据）→ T-0 04:00 ET 刷新 → T-0 07:00 ET 再刷新**（防线：日历改期、相位由 EMPTY 变已知、新增当日事件）。
- **盘后计划**：**T-0 15:45 ET 生成**（用当日 BMO 名单；B5 证明那时 actual 已可得）。
- 载体：新增/改一行 cron（与入场执行器同一目录惯例，`>> logs/ext_entry_plan.log`）。
⇒ **设计影响**：计划要带 `generated_at / refreshed_at / source_versions`，且**允许"空计划"**（今天没有事件 ⇒ 计划为空 ⇒ 执行器整轮早退 ⇒ 这本身就是 C5 的收益）。

### Q5 —— 计划的粒度与生命周期？
**每票一行（不是每轮一行）**，状态机：
```
planned ──(相位窗到)──▶ armed ──(数据未到)──▶ waiting_data ──(数据齐+过闸)──▶ ordered
                          │                        │
                          └──(闸拒/失效)──▶ rejected(reason)   └──(窗尾)──▶ expired
```
幂等键 `(et_date, symbol, session, phase)`；**每票只走一次**（不是每轮从头重算）—— 这是"程序性去无用功"的正解。
⇒ **设计影响**：状态存在计划文件里（读-改-写，带文件锁，与 `_state_lock` 同款），执行器每轮只做"推进状态 + 复核事实闸"。

### Q6 —— 计划与"闸"的关系？（**不变量**）
**计划只定"看谁"，不定"做不做"。** 判定权仍在下单时的门链（判据①②③/分档量闸/价差/深度/费用），且**执行时复核**（fail-closed）。计划卡里带"门槛快照"仅作**审计与漂移检测**（对比"计划时门槛 vs 执行时门槛"），**不作为放行依据** —— 这正是 UE 的 `enforce_at_execution=true, applied_here=false` 语义（A2）。
⇒ **设计影响**：杜绝了最危险的失败模式"计划过期 ⇒ 下错单"；计划过期最多导致**错过**。

### Q7 —— 榜单怎么办？（**反方关键**）
**保留，但降级为"观测 + 补漏候选"**：不参与判定，只记录"若按榜单会怎样"。理由：① C2 显示 9/22 榜单是**唯一供给**（当时无日历源）—— 日历覆盖有缺口史实（futu 单源只覆盖 39%）；② 补漏要变成**常设读数**（"事件票来自榜单 N / 来自日历 M"），而不是我今天的一次性对账。
⇒ **设计影响**：执行器**不删任何源**，只把"谁的票进了闸"标出来；跨日读数（复核日 10/08）若持续 N=0，才谈"关榜单"。

### Q8 —— 计划过期/错位怎么兜？
四道：① **多次刷新**（Q4）；② **执行时复核**（Q6）；③ 计划卡带**失效条件**：`phase_conflict`（源间打架，B4）、`date_changed`（改期）、`source_missing`；④ **双源并集**生成（futu ∪ Finnhub ∪ AV），任何单源缺失都不致空计划。
⇒ **设计影响**：计划卡必须是"**多源并集 + 每源证据**"的形态，不是单源快照。

### Q9 —— 判据②"数据迟到"怎么进计划？（**这是计划相对盲扫的真增量**）
计划卡带 `data_expectation`：`{basis: 'BMO'|'AMC', expected_available_after_et: '08:05'|'04:00', fallback_days: [-1, 0]}`，且 `fallback_days` 直接复用 RFC-102 §2.6 的"取数日并源"。
⇒ **设计影响**：执行器从"每轮撞运气问一次"变成"**按计划里的时刻表去问**"：BMO 票在 04:00–08:00 之间**不空转**（状态停在 `waiting_data`，不重复取数），08:05 后开始问；AMC 票 04:00 直接问。既省调用又让台账可读（"今天 4 只票在 waiting_data，命中 1 只"）。

### Q10 —— 计划化能**多出单**吗？（必须对用户明说）
**不能。** 出单卡点是 B6（量闸墙）+ 盘前价差（CBRL 实测 12.4%）+ B5（actual 迟到），与"怎么发现人群"无关。
⇒ **设计影响**：本设计的验收标准**不是**"出单数"，而是三条可测指标：① 结构性死票占用（票次/日）从 ~4,300 → ~50；② 单份可读工件（1 个计划 + 1 本对账台账）替代现 4 本拒绝台账 + 3 个影子拼图；③ `waiting_data` 命中率（数据何时到 ⇒ 直接服务 RFC-102 的复核判据）。

### Q11 —— 计划化的**新风险**是什么？
**新失败模式：计划成了"决定"。** 一旦有人（或未来的我）把"计划里有这只票"读成"这只票合格"，链路的 fail-closed 性质就破了。另外：计划文件损坏/半写（⇒ 用 `app/utils/atomic_write.py` 原子写）、文件锁竞争（⇒ 与 `_state_lock` 同款）、计划与执行器时钟错位（⇒ 计划内所有时刻都写 **ET**，执行器用 `utils/et_time`）。
⇒ **设计影响**：**三条硬不变量写进代码注释与测试**：① 计划不含方向；② 计划不含放行；③ 计划损坏 ⇒ 整轮 fail-closed（不下单、只告警）。

### Q12 —— 这与已回滚的 RFC-101（L2 缓存）以及被证伪的 α 是什么关系？
它们是**同一个动机的两种错解**：都试图在"每轮重复评估已知答案"上省事。第一性原理的答案是——**问题不在"每轮重复"，在"人群里 95% 的人根本不该被评估"**。计划化把人群一次性缩小到计划内，于是：① 不需要缓存；② 不需要负缓存；③ 不需要"集合替换"（α 会改归因的那条路）。
⇒ **设计影响**：RFC-101 的 L2 **保持回滚状态**（`3d3b37eeb`），本设计**不复用它任何代码**；α 保持未装。设计文档里记这一笔，防后人重走。

## 4. 历史坑映射（每条 → 本设计如何规避）

| 坑（历史） | 本设计的规避 |
|---|---|
| 死门三路径（门恒不触发：值同源/错相位/产物被仲裁丢弃） | 计划卡带 `gate_snapshot` 与 `expectation`，对账台账记录"门是否真的可能触发"（如 B6：量闸在事件票上恒拒 ⇒ 明确标注"当前档位下量闸=墙"，不假装它是活门） |
| 观测与决策解耦 | 计划**只读不判定**；榜单降级为观测；计划本身不参与放行 |
| 观测量同源（carry 影子曾用扁平 20 万判生产分档） | 计划卡的 `gate_snapshot` 必须由 `EXEC._min_volume_now(session, hour)` 等**同一函数**生成（禁复制常量） |
| N4 环境耦合（`.env.us` 一改开关，依赖"默认关"的用例即红） | 计划生成器/消费者都用**显式注入**（`session`/`plan_path` 参数），测试用 tmp 路径；开关默认值断言写在源码契约测试里 |
| 棘轮（`except: pass` 不得增加） | 新代码零 `except: pass`；`except Exception` 必须带显式告警与降级路径 |
| 双实现漂移（相位判据出现在 3 处） | 计划生成器**必须**调 `_session_event_pairs` + `_parse_earnings_phase`（现函数），并加**第三处**的源码契约测试 |
| 影子融合纪律（只融生产者活着的同族） | 对账台账的生产者=执行器（活着）；不新造"只有消费者没有生产者"的台账 |
| 计划过期（**新坑**） | Q6/Q8 四道兜底；测试钉"计划损坏 ⇒ 不下单" |
| 测试直接下单（P1 事故） | 计划生成器不含任何交易调用；消费侧新测试一律 mock 券商路径（`_open_trade_context` 桩） |
| 时区三格式混存 | 计划内一律 **ET 字符串**（`utils/et_time`），禁止自写 −12h |
| 共有文件纪律 | 新文件独立；`extended_hours_entry_executor.py` 有他 agent WIP ⇒ 落地时用 worktree + 只提交自己 hunk |
| 一次一变量 | 本设计**只改人群发现方式**；计划生成器先以"影子"形态上线（阶段 0/1），切换消费单独一批 |

## 6. 待裁问题（frontier：现在就能答、无需再查的决策）

❓ **Q-A 载体**：计划工件用 **丙（文件 + 影子入库）**，还是直接上 **乙（新表）**？
➡️ 推荐丙。理由：RFC-101 教训（先造设施、收益 0 再回滚）；丙零碰钱链、可随时删。

❓ **Q-B 计划含不含"闸前预筛"**：计划生成时是否就用**便宜闸**（价格/市值/换手）先筛一遍，把明显不可能（如 <$5 仙股）挡在计划外？
➡️ 推荐**含**（这是"去无用功"的另一半），但预筛必须用**与执行时同一函数**（禁复制阈值），并把被预筛掉的票写进计划文件的 `prefiltered_out[]`（可审计，不静默）。

❓ **Q-C 榜单的归宿**：保留为"观测+补漏"（推荐）还是彻底关掉？
➡️ 推荐**保留观测**，直到跨日读数（复核日 10/08）证明补漏恒为 0。

❓ **Q-D 计划要不要携带"预期收益/费用"字段**（像 UE 的 `cost_coverage`/`executability`）？
➡️ 推荐**先不带**（费用模型在下单时算，且延长时段价差不可预测），只带 `gate_snapshot`；否则计划里出现"看起来能做"的数字，正是 Q11 的失败模式。

❓ **Q-E 谁来做**：本设计由我实现（阶段 0）还是写进 RFC-104 走多模型审查先行？
➡️ 推荐：**先写 RFC-104（含本设计要点与回滚判据）**，再实现阶段 0。

## 7. 与既有 RFC 的关系

- **RFC-100/102/103**：量闸分档 / 盘前 AMC 配对 / 放宽影子 —— 这些是"闸与人群的语义"，本设计**不改它们的任何取值**，只改"谁进闸"。
- **RFC-101（已回滚）**：本设计取代其动机；§2 Q12 已留痕，防重走。
- **RFC-099（方向判据）**：方向判据仍在下单时的门链；本设计不给方向 ⇒ 无冲突。
