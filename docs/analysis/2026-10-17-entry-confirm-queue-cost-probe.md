# 门确认后「执行队列成本」实测 (probe: 队列延迟是成本还是收益)

- 日期: 2026-10-17
- 缘起: 用户讨论「开盘后 5min 开始交易、每循环 3 笔、2min 门检查迭代有延后 ⇒ 能否全并发/更优方案」
- 脚本: `scripts/probe_entry_confirm_queue_cost.py` (只读: jsonl + sqlite mode=ro, 零写入)
- 数据: `data/shadow/entry_confirm_forward.jsonl` (v1 21 行 + v2 5 行 CONFIRMED) × `ftseek_us.db.trade_records` (PLAYBOOK_SIM)

## 0. 机制前提 (代码实证, 2026-10-17)

1. **门检查已是全并发**: 所有过闸指令在同轮全部 arm (`_cycle_new_count` 只在真实成交 +1,
   auto_execute_flow.py:1125); 判定由 10s 快循环 sweep 各自独立进行 (scheduler_core.py:2951),
   读 Futu 推送共享缓存, 同 tick 毫秒级完成。
2. **串行只在 CONFIRMED→成交**: 等下一个 180s 主循环 + `max_new_positions_per_cycle=3`。
3. **确认后触发闸每轮复验** (auto_execute_flow.py:274-277): 价格回落须等再突破当日高/低点
   ⇒ 长延迟大多是**触发复验**而非 cap 排队 (10/12 全日仅 5 笔成交、10/15 仅 3 笔, cap 根本不饱和)。

## 1. 口径

- 基准价 = confirm 时刻立即市价成交的对手价: v2 行用 ask/bid_at_confirm (精确);
  v1 行只有 px_at_confirm (last trade, 粗口径, 单独标记不混算)。
- `imp_bps` 方向感知: LONG=(bench−fill)/bench, SHORT=(fill−bench)/bench; **正值=延迟让成交价更好**。
- 分桶: lag=fill−confirm; ≤200s=下一轮即成交; 200-400s=cap 排队候选; >400s=触发复验。

## 3. 结论

1. **「延后 = 盈利受损」在本样本不成立, 方向相反**: 延迟成交的入场价中位改善 4.1bps,
   队列日 (10/14, 唯一 cap 真正饱和的早晨) 4 笔排队单改善全部为正 (+2.7~+158bps)。
   与 RFC-145 §2.4 chase_cap 面 (拦后成交中位改善 53.1bps) 方向一致: 当前 regime 下,
   开盘窗的等待是**价格收益**不是成本。若放开 cap/加快节奏, 按本样本约吐回 **$364/24笔
   ≈ $73/交易日** 的入场价改善。
2. **交易净盈亏面, 延迟没有选出更好的交易**: queued 桶净 −$126.79 — 但由 CAT
   OVERNIGHT_GAP_STOP −$302.52 单笔主导, 该族是 RFC-141 §5.8 已判的「地平线错配」
   (2min 尺量不到 6-19h 恶化), 与队列无关; SL_INITIAL (COIN −$141) 落在立即成交桶。
3. **触发闸复验是未被记功的隐式二次确认**: SNOW (+193.5bps, +$114) / AMD 10/15
   (+134.7bps, +$37) 的大改善全部来自「确认后价格回落 → 等再突破」的复验等待,
   不是来自 cap。这层保护在任何「加快执行」方案里都必须保留。
4. ⇒ 对原问题的回答: **检查侧已全并发 (无需改); 执行侧加速/放开 cap 的预期收益为负**;
   真正的盈利杠杆维持在费用线 (费=毛利 1.48×) 与 SL_INITIAL 族 (RFC-145 §3 结论不变)。

## 4. 局限 (裁决日引用前必读)

- n=24, 仅 5 个交易日, 且 v1 行是 last-trade 粗基准; v2 精确口径仅 5 行。
- regime 依赖: 本周等待有效 (均值回归 tape); 强动量 gap-and-go 日等待会是成本, 本样本看不到。
- imp_$ 只量入场价, 不量交易终局; 净 pnl 列受单笔大亏主导, n 小不可分。
- 复跑: `python3 scripts/probe_entry_confirm_queue_cost.py` — 随 RFC-141 v2 前瞻窗攒样,
  v2 精确口径行数会自增, 建议裁决日前复跑一次。
