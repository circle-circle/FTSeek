# 采集"用得上"的判据与本次停采实测（2026-09-21）

**用户问题**：如何能让采集真正有效用上？如果无效就停。
**答案一句话**：采集"用得上"的唯一入口是**立项时就有一个会被判据改变的决定**（消费者）；
判据 FAIL 只是"这条研究假设死了"，**不等于**"数据没用"——本次差点因此停掉一条喂着**生产门**的料。

---

## 1. 判据：一条采集算"用得上"，要同时满足四条

| # | 条件 | 怎么验（可执行） |
| --- | --- | --- |
| 1 | 有**预注册判据**（先定后看，含 min_n 与裁决口径） | 注册表条目 `graduation_criteria` 非空 |
| 2 | 有**消费者**：判据通过后**哪个决定会变** + 谁执行 | `grep -rln <产物文件名> app/ scripts/ ops/` 找**交易路径**消费者；只有 eval/注册表自己 = 无消费者 |
| 3 | 有**到期与执行人**（到期未裁 ⇒ 停采，不是挂着） | `ADJUDICATED.recheck_after` + 周检通知（已有） |
| 4 | 判据 FAIL / 过期未续 ⇒ **停采**（显式，数据保留） | 见 §3 采集闸 |

**新增门槛（本文件的规则，写给未来立项的人）**：任何新影子/新采集，注册时必须写出"若判据通过 →
**哪个决定会变 + 谁执行**"。**写不出 = 不给立项**。这是"用得上"的唯一入口条件——
8/12 那批通道的病根就是"先采着、以后说不定有用"，于是判据写完了、样本也够了，**没有任何决定挂在上面**。

## 3. 机制：停采必须"显式 + 每通道一开关"（本次落地）

代码：`scripts/futu_channel_shadow_collect.py::_collector_gate()`，四路采集在调用点全部过闸。

1. **显式两道**（任一命中即停采，数据一律保留不删）：
   ① 登记里 `collection_retired=True`（带理由）；② 该通道独立开关
   `futu_channels.<channel>_collect_enabled=false`。
2. **反推禁令（写进代码注释与测试）**：**不许**从判据状态（KILLED/FAIL）反推是否停采。
   实锤：`capital_flow` 原料喂着生产门，若按状态自动停采会**静默断料**（门 fail-open 退化为无门）。
   ⇒ 注册表新增 `collection_retired` 字段，与 `status` **刻意分开**。
3. **补上缺失的开关**：`capital_flow` 过去**没有**独立开关（只有总闸），这本身就是"想停也停不了/一停停一片"的成因。
4. **可见性**：停采记一行 INFO（`停采 <id> — 开关 ...=false`），不是静默。

验证（本次实测）：`_collector_gate` 实跑 ⇒ 采/采/**停**/采（仅 iv_hv）；线上配置实值
`shadow_collect_enabled=True, capital_flow=True, ofi=True, iv=True→False, movers=True`；
端到端测试证明"只调过闸的采集函数"（`tests/test_futu_channel_collect_gate.py`，5 例，含反推禁令的回归钉子）。

## 4. 诚实边界

- iv_hv 停采后**不再有新样本**；若将来要测"财报前后 IV crush"，需新假设 + 新预注册 + 翻开关，
  且那类问题本质需要**前向**采样（历史 32K 行能提供的有限）。
- `top_movers` ③同轴并入**尚未实现**——本文件只确认"采集必须继续"，不等于③已落地。
- 相邻发现（不在本次处置范围）：`reentry_gate_effect_report.json` 的读数方向反直觉——
  `gate_would_block` n=9 均值 **−6.63** vs `gate_pass` n=44 均值 **−17.77**（全样 53 笔均值 −15.87）。
  即"被拦的笔比放过的笔更好"，门的**选择方向**可疑（n 小、窗口单侧）；门确实减亏 $59.63，
  但这只说明"拦掉亏的"，不说明"拦对了"。**另案裁决**，不能靠停采解决。
