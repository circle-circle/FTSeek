## 2. 根因（一句话）

**循环是"先扫一大票人群、再层层筛"，而资格的必要条件（当日同相位财报事件）只覆盖其中个位数；同时载体每 5 分钟换进程，导致所有中间结果只能重算。**

两个根因互相独立：
- **人群错配（结构性）**：榜单主体是 <$5 的微盘泵票（被拒票 100% <$5、价中位 $1.4）⇒ 96% 的候选**在资格上就不可能成交**；
- **状态丢失（工程性）**：跨轮零复用 ⇒ 同一个已知答案每 5 分钟重算一次（重复 9–12x）。

## 4. 可选方案（8 个，按"动作发生的位置"分四族）

### 族 1｜输入侧（改"看谁"）

#### 方案 E：**资格审查倒推候选（qualified-first）** ⭐ 推荐主线

- **核心思路**：把循环反过来 —— 先取**当日同相位财报名单**（实测 5–6 只/日，已有 `_calendar_symbols` / Finnhub 并源），再**逐票取数 → 评估 → 下单**；异动榜**降级为纯观测源**（只进 prefilter 影子与"若放宽事件门会多出多少"的反事实台账）。
- **为什么这是根因解**：见 §1-d —— 非事件票**在门链上必然被拒**，扫它们不产生任何一单；而"重复 10x"的主体正是这批票。
- **实测收益**：每轮评估 42 只 → **5–6 只（−86%）**；配合 C1 可证明**输出等价**（事件池是资格的必要条件集合）。
- **优点**：不改门链、不改资格语义、可证明等价；顺带把"榜单每轮 1 次 + 逐票快照/K 线"的调用面砍到事件池规模；架构上"事件驱动"名实相符。
- **缺点 / 风险**：
  1. **覆盖缺口变成唯一供给约束** —— 事件池漏票即漏机会（实测主源只覆盖 Finnhub 的 39%，并源后 6/6；相位未标定 11.8% 仍在）；
  2. 若**未来放松事件门**（如"隔夜 carry 路线"），E 的供给面会过窄 ⇒ **必须保留榜单观测**并把"被观测到但不可交易"的票记全（现已有 `prefilter` 影子 + near-miss 台账，需补一条"事件池外但过价格闸"的计数）；
  3. 榜单的另一个用途（发现"跳空≥3% 的非财报票"）在现行门链下**无交易价值**，但作为空侧规则演化的证据面仍要看 —— 观测与决策解耦（既有纪律）。
- **适用条件**：接受"事件池是供给唯一入口"这一事实（数据支持）。

#### 方案 F：榜单侧预筛（站在源头过滤）
- **核心思路**：榜单每轮已返 `turnover_ratio` / `volume_ratio`（见 `data/futu_top_movers_shadow.jsonl` 字段），先用它们把 50 只砍到 top N（如 10），只对 top N 做逐票快照/K 线。
- **收益**：逐票网络调用降 ~80%。
- **风险**：预筛顺序与最终闸不同源（`volume_ratio` 高 ≠ 换手达标）⇒ **可能漏票**，需影子对照（预筛放过 vs 全量评估的差值）。
- **评价**：**比 A/B 弱、比 E 差**——它省的是"评估"，但没解决"人群错配"；若已做 E，F 基本被 E 覆盖。**留作 E 的补强**：事件池内若某日过多，再用 F 排序。

### 族 2｜计算侧（改"算多少"）

#### 方案 A：**结构性负缓存 + 榜单驱动失效**（零行为变更）

- **核心思路**：磁盘缓存 `data/ext_entry_round_cache.json`，键 `{ET日}:{session}:{symbol}`，值 `{class, reason, snapshot:{px,chg,vol}, until}`。只缓存"日内结构不翻闸"的类别：

| 类别 | 判据 | 有效期 | 失效条件 |
| --- | --- | --- | --- |
| 价格远低于下限 | `price < 0.5 × MIN_PRICE` | 整段 session | 榜单行 chg 相对快照**跳变**（如 ≥ +30pp）⇒ 立即重评 |
| 市值远低于下限 | `mktcap < 0.8 × floor` | 整段 session | 不失效（日内市值不翻倍） |
| 无当日同相位财报事件 | `calendar_missing` | 整段 session | 每 30 分钟复检（Finnhub 迟到） |
| 结构性死票（ETF 等） | 既有 ETF 滤除 | 整段 session | 不失效 |

- **关键设计**：榜单**每轮照读**（1 次调用，便宜），用榜单里的 px/chg/vol 与缓存快照比对 ⇒ **票一动就回队列**。这是"增量"之所以安全的原因。
- **收益**：评估次数 11,698 → ~2,000/5 日（**−83%**）。
- **优点**：**零行为变更**（结构性类别可证明等价）；失败即忽略 ⇒ 退化为现行为（满足 C5）。
- **缺点**：不省 **OpenD 连接**（cron 每轮仍新连）；多一个状态文件要防并发/损坏（需原子写 + 读失败忽略）。
- **适用条件**：任何方案组合都可叠加。

#### 方案 B：跨轮结果缓存（把算过的答案也留下来）
- **核心思路**：把日历 / Finnhub 当日表 / 逐票财报判据 / 市值也放进同一缓存，TTL 按可变性分：`actual_missing` **10 分钟**、`surprise_stale`/`period_unparseable` **整段**、正结果 **整段**、市值 **整段**。
- **收益**：逐票网络调用 → 每 session 数次；每轮墙钟 10s → 预计 3–5s。
- **风险**：**fail-close 长缓存会把"数据迟到"钉成"永久拒绝"**（C3）⇒ 必须按原因分 TTL + 打印"命中/过期重算"计数。
- **评价**：与 A 同一文件、同一套读写；**A+B 是"不动架构"下的最优组合**。

### 族 3｜载体侧（改"跑在哪"）

#### 方案 C：常驻循环进程（省连接的那一刀）
- **核心思路**：入场链由 `*/5 cron` 改为常驻 `while True: collect(); sleep(60)`（flock 防叠加 + 崩溃恢复 + 日志轮转），进程内缓存天然跨轮，OpenD 连接复用。
- **收益**：**OpenD 连接次数 113 次/日 → 1 次**；A/B 的缓存可退回进程内（更简单）。
- **风险/代价**：日志轮转、state 原子性、崩溃重启、孤儿进程、与 systemd 的集成；属**调度载体迁移**，需单独立项与预注册（仓库有对应技能与先例）。
- **评价**：**唯一能省连接的一档**；但工程面最大，且与 E 正交（E 降评估量，C 降连接次数）。

#### 方案 H：从零重设计 —— 入场+退出合并为**单个分钟级常驻事件循环**
- **核心思路**：退出链已是 `* * * * *` + 会话门控 + delegate；把入场也纳入同一 daemon（分钟级 tick），共享 qctx/tctx 与缓存，按"到期调度"驱动（见 G）。
- **收益**：连接与状态复用最大化；观测面（每分钟一行）统一；未来加方向/规则不再新增 cron 行。
- **风险**：单点故障面变大（一个进程挂 = 入场+退出都停）⇒ 需要进程守护 + 心跳 + 失败告警（退出链已有的逐轮 rc 契约要搬过来）。
- **评价**：**上限最高、代价最大**；建议在 E+A 跑稳后作为第二阶段候选，不要与本期混做。

### 族 4｜调度侧（改"多久看一次 / 何时看"）

#### 方案 D：死区降频
- **核心思路**：按实测量分布（04:00–07:00 中位量 398–2,640），把 04:00–07:00 的 `*/5` 改 `*/10`。
- **收益**：轮次 −50%（死区）；调用量同比例。
- **风险**：**与 RFC-100 方向相反**（刚给早段放宽了量闸），且有**行为变更**（少一半检查点 ⇒ 可能错过早段瞬时达标）。
- **评价**：**不建议现在做**；若要做，须与 RFC-100 的观测读数（复核日 2026-10-08）一起裁。

#### 方案 G：状态机 / 到期调度（真正的"增量"泛化）
- **核心思路**：每票记 `next_check_at` 与**条件**（"量到 15 万再看"、"chg 回到带内再看"、"Finnhub actual 已到再看"），把"每轮全量重扫"变成"到期才看"。本质是 A 的泛化（A 只处理"永不变"的类别）。
- **收益**：理论上最优（只算"可能变好"的票）。
- **风险**：复杂度最高、最难审计（"为什么这轮没看它"变成要读调度状态）；条件写错 = 静默漏票（C4 的台账变成必须）。
- **评价**：**中期形态**；建议先用 A 的极简版 + 观测数据验证"条件式跳过"的漏票率，再决定要不要泛化。

#### 方案 I（工程细节，可选）：缓存介质用 SQLite 而非 JSON
- 理由：并发写/原子性/可查询统计（"今日跳过 N 只、按类别分布"）都比 JSON 稳；仓库已有 SQLite 惯例。
- 代价：多一个 schema 要迁移；收益主要是健壮性，不是性能。
- 评价：**A/B 落地时顺手决定**即可，不单列决策。

## 6. 反方审查（自己先攻一遍）

1. **最可能失败点：把 E 做成"只看事件池"后，我们失去了"榜票也能成交"的可能** —— 但 §1-d 实读证明门链对 LONG/SHORT **都**要求当日同相位事件 ⇒ 榜票在现门链下**不可能成交**。反方仍成立的部分：**若未来放松事件门**，E 需要立刻扩源 ⇒ 因此 E 必须**同时保留榜单观测**（prefilter 影子 / near-miss 台账 / 新增"事件池外但过价格闸"计数），把"供给被门锁住"与"供给本来就没有"分开。
2. **20% 复杂度吃到 80% 效果**：E（组织候选）＋ A（结构性负缓存）两件小事就覆盖了本文 90% 的浪费；**B/C/G/H 都不是必需**。若只能做一件，做 E。
3. **激进提升方案**：把"分钟级轮询"改成"事件驱动"（财报发布时刻表 → 定时唤醒；盘前量阈值 → 探测命中才唤醒）。技术上依赖 futu 无推送能力（只能自建探测器轮询），**收益不如 E 大**，暂不推荐。
4. **从零重设计**：如果今天重写这条链，我会做：单一常驻事件循环 + 事件池驱动 + 状态机到期调度 + 全量落 SQLite（= H+E+G+I）。但**现在不该重写**：它把三个独立变更（载体/人群/调度）打包成一次不可归因的改动，违反"一次只改一个变量"。
5. **优化本身的风险**：任何"跳过"都会让日志看起来更"干净"（评估数下降）⇒ **必须留跳过台账 + 反事实**（C4），否则下次"为什么没单"的归因会比现在更难。

## 7. 建议（按证据强度排序）

1. **做 E（主线）**：候选组织改成"事件池优先"，榜单降级为观测；**判据 = 同轮 A/B 闸计数与 ordered 逐字一致**；同时补一条"事件池外但过价格闸的票数"计数（供给约束可见化）。
2. **同时做 A**（事件池自身也会有重复评估：每轮 5–6 只 × 113 轮仍会重复）——E+A 一起上，成本低、风险低、可证明等价。
3. **B 紧随其后**（同一文件、同一套读写；按原因分 TTL，`actual_missing` 短 TTL）。
