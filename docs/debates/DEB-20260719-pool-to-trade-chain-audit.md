## 背景

上线前最后一轮链路审计。前两轮 (DEB-20260719-pre-live-audit / round2) 已覆盖资本正确性/风险真值/退出链/重启恢复/SQLite并发/SSOT。
本轮聚焦**单支股票从进池到成交的分析链路本身**是否合理、是否存在"静默失败"和"盘中信号失效未复核"两类风险。

链路七段 (确认现状, 均为 read-only 审计结论):

```
Stage1 进池(4层+SCAN) → Stage2 数据采集(6维) → Stage3 筛选 → Stage4 决策(投票/DA)
  → Stage5 指令构建 → Stage6 触发执行 → Stage7 退出监控
```

**已确认的架构事实 (无需再辩, 作为前提)**:
- 运行时**零 LLM 调用**。DA 分析由仓库外 Hermes skill 盘前预计算, 序列化为 `data/opportunity_scan_YYYY-MM-DD.json`, 管线按文件消费 (`pipeline.py:387-457 BridgeVotingAdapter`)。这是 2026-07-11 "双脑清理" 的正确取舍, 本轮**不推翻**。
- 三适配器优先级: Bridge > TechnicalFallback(纯函数) > Null(全SKIP)。
- 指令构建全确定性 (`instruction_generator.compute_instruction_values`), SL/TP 受 vol_bucket 钳制。
- 所有来源 (POSITION/PLAN/MANUAL/INTRADAY/SCAN) 下游处理一致, 来源只影响执行优先级与淘汰排序。

## 目标

回答: 当前"标的→分析→成交"链路在上线前是否需要补齐? 具体决策以下 6 个问题各自的处置 (修复/延后/不做):

- P1 类 (静默失败, 建议上线前修): #1 Bridge 缺失无告警, #2 盘中 thesis 失效未复核

## 问题清单与可选方案

### 问题 #1 [P1] Bridge 文件缺失/损坏 → 静默降级, 无告警

**现状**: `_try_load_bridge()` (pipeline.py:460-526) 读不到或 JSON 解析失败时, 返回 None →
`BridgeVotingAdapter` 缺席 → 降级 `TechnicalFallbackAdapter` → 若 voting_coordinator 为 None 则 `NullVotingAdapter` 全 SKIP。
整个过程**只有 log 行, 无任何告警/飞书推送**。若 Hermes cron 失败或模型超时, 系统可能一整天 0 决策而运维不知情。

- 方案 A: `run_playbook_generate` 检测到"当天应有 bridge 但缺失/为空/schema 非法"时, 走 `feishu_push` 发一条告警 (复用现有 PlaybookPusher)。附带降级到哪个 adapter。
- 方案 B: 加轻量 schema 校验 (candidates 是 list、每项含 symbol/direction/decision_id), 非法则告警 + 拒绝消费 (不静默接受半损坏文件)。
- 方案 A+B (推荐): 缺失/为空/schema非法 三态统一告警, 且 schema 非法时 fail-safe (视作缺失, 走技术面降级而非消费坏数据)。

### 问题 #2 [P1] 盘中 thesis 失效未复核, 触发纯价量机械判断

**现状**: bridge ~9:00 ET 写入方向/thesis, `_check_intraday_trigger` (pipeline.py:2789-3112) 在盘中数小时后按"突破日高/日低+量能"触发。
触发时**不重新校验** 方向/财报/新闻。示例: MCK(7/17) bridge 写 LONG, 下午逻辑已反转但仍机械触发, 死扛4h亏损。

- 方案 A: 触发时做"硬失效"检测 — 财报日历重查 (若触发时距财报<1天则 SKIP)、极端反向gap已有(8%门), 补一个"当日相对bridge写入时价格已反向漂移>X%则 SKIP"。轻量、确定性、无LLM。
- 方案 B: 触发时调 LLM 复核 thesis (轨道B thesis_recheck, feature_flag 已存在默认off)。重、慢、违背"运行时零LLM"原则。
- 方案 C: 缩短 bridge→触发的时间窗 (只在开盘后 N 小时内允许触发, 过期指令失效)。已有 24h TTL, 可收紧到当日 morning-window。
- 倾向: 方案 A (确定性失效门) + 方案 C (收紧触发时间窗) 组合; 方案 B 留在 shadow 观测, 校准后再定。

### 问题 #3 [P2] SCAN 注入绕过池管理 (无TTL/无容量上限/不同步内存)

**现状**: `_try_load_bridge` L498-524 直接写 `daily_active_pool.json`, 追加 `source=SCAN, expires_at=None`。
绕过 `DailyActivePool` 的 typed API、`_cleanup_expired`、`MAX_POOL_SIZE`/`MAX_INTRADAY_ALERTS` 容量控制, 且不同步内存单例。
后果: SCAN 条目跨日不清理、无容量上限、内存与磁盘状态可能不一致。

- 方案 A: 让 bridge 注入走 `DailyActivePool.add_*` 正规 API, 赋 24h TTL + 纳入容量淘汰。
- 方案 B: 只补 `expires_at` (24h) 让 `_cleanup_expired` 能回收, 最小改动。
- 倾向: 方案 B 上线前做 (最小), 方案 A 样本期偿还。

### 问题 #4 [P2] 数据新鲜度不一致 (技术5min vs 基本面/财报日缓存)

**现状**: 技术面每5min刷新, 基本面/内幕/财报日缓存。盘中财报意外或新闻不会在触发前被重新评估。
与 #2 部分重叠 (财报重查可一并解决)。

- 方案 A: 触发路径对"财报日期"这一项强制实时重查 (其余维持日缓存)。与 #2-A 合并实现。
- 方案 B: 全维度触发时刷新 — 成本高, 打爆 Finnhub 限流, 不推荐。
- 倾向: 方案 A, 与 #2 合并。

### 问题 #5 [P2] 筛选缺流动性/价差过滤

**现状**: `PlaybookScreener` 无 ADV/市值/spread 门。微盘股能进到 Stage4 浪费投票, 才在 Stage6 报价健康门被拒。
注: 已有 pretrade_quote_gate (spread<5%, age<60s) 兜底, 故为浪费算力而非风控漏洞。

- 方案 A: 筛选阶段加最小 ADV/市值门 (数据已在6维里)。
- 方案 B: 不做 — quote_gate 已兜底, 当前 watchlist 均为大盘股, 无实际微盘风险。
- 倾向: 方案 B (延后), 除非 watchlist 扩容到小盘。

### 问题 #6 [P3] "2模型"非独立 + factor_exit 字符串匹配静默默认

**现状**:
- bridge confidence 由"challenger 是否同意"合成, 但两模型是同一 LLM 两次对抗性提问, 非独立评判 (confidence 已知 r=-0.211 负相关, 故已不按其放大仓位)。
- `factor_exit` 规则按因子名字符串匹配 (`playbook_horizon.yaml`), 新因子漏注册则静默默认"无 factor 退出", 无告警。

- 方案 A (factor_exit): 加载因子时校验退出规则存在, 缺失则 WARN 日志 (至少不静默)。
- 方案 B ("2模型"): 不动 — 已知 confidence 不校准且不用于放大仓位, 属长期 backlog。
- 倾向: 方案 A 顺手做 (一行 WARN), 方案 B 记 backlog。

## SIM 放量与数据质量 (问题 #7–#12)

> **与 #1–#6 的关联**: 上半部分回答"链路是否合理" (静默失败 + 盘中失效)。本部分同一条链路, 换视角回答用户核心诉求——**SIM 阶段如何在不损数据质量的前提下增加成交量, 更快达成毕业标准**。
> 关键前置结论: **成交量瓶颈不在风控闸门, 而在"供给(#7) + 入场带触发(#8)"两处**; 且已采集但未消费的 shadow 数据(#11)可低成本替代真实成交量。
> 与 #5(流动性门)相反方向——#5 讨论"要不要加过滤", 本部分讨论"哪些过滤在 SIM 该放松"; 二者须一并裁决, 避免相互抵消。

**实证前提 (14 交易日 + telemetry 实测)**:
- 毕业标准 (config `unified_config.yaml:1219-1228`): 50 笔 / 45% 胜率 / 正 PnL / IC≥0.03 / 回撤<8%。现状 83 笔 / 43.4% / -$976.93。
- 供给天花板: DA 5–10 + UE 0–5 = 5–13 候选/天。入场带触发率仅 **7%** (`entry_timing_shadow.jsonl` 576 行: 40 触发 / 229 被 VWAP 拦 / 307 自然未入带)。
- 净成交 ≈6.5/天, 供给→成交效率 50–80%, 闸门余量不大 → **抬量必须同时动供给与价格带门**。
- 排查 14 道闸门, 仅 2 道真约束; 以下均**非约束或不在 playbook 路径**: daily_notional_cap(仅用47%)、max_daily_positions(用34%)、confidence门(DA直写DB绕过, 见 pipeline.py:2163-2172 死配置)、IC硬阻断(仅冻结主线, playbook 零引用)、PDT/熔断/财报门(均不在 auto_execute 路径)。

### 问题 #7 [P1-放量] Bridge 候选供给不足 (5–10/天) 是成交量天花板

**现状**: 即使下游全放开, 单日成交 ≤ 候选数。DA skill 为仓库外 Hermes, 当前每日 5–10 只; UE (`universe_expansion.entry_enabled=true`, cap 30/天) 实际只产 1–2/天 (扫描率低, 非 cap 限制, `llm_universe_scan.jsonl` 仅 10 行)。

- 方案 A: 请 Hermes DA 每日出 12–15 只 (仓库外动作, 需用户协调)。**唯一能抬天花板的杠杆**。
- 方案 B: 提高 UE 扫描频率/降低 UE 入池门槛, 让 UE 从 1–2/天 → 3–5/天 (仓库内可调)。
- 倾向: A+B 并行; A 是根因, B 是仓库内可立即执行的补充。
- **关联 #3**: 供给增加会放大 #3 (SCAN 无 TTL/无容量上限) 的池膨胀风险 → #3 必须先修或同批修。

### 问题 #8 [P1-放量] 入场带过窄, 93% 候选从未触发

**现状**: `entry_band.py:20-21` `CHASE_ZONE_PCT=0.05, KNIFE_FLOOR_PCT=0.03`。`trigger_miss_telemetry.jsonl` (990 行): runaway_up 334 / runaway_down 241 / vwap_block 180 / extreme_gap 136 / knife_below 79 / reanchored 13。已有 reanchor 路径 (`pipeline.py:3009-3023`, `entry_reanchor_max_drift_pct=4.0`) 但仅救回 1.3%。

- 方案 A: 入场带 (5%,3%) → (7%,4%), 仍在 extreme_gap 8% 天花板内; reanchor drift 4%→6–7% (config 热加载)。预期 +20–50% 成交。
- 方案 B: 不动带宽, 只靠供给(#7)。缺点: 供给是仓库外, 见效慢。
- 倾向: 方案 A (低风险, 仓库内, 立即见效)。
- **关联 #2**: 放宽带宽会让更多"漂移较大"的老指令触发 → 加剧 #2 (盘中 thesis 失效); 故 #8 放量必须与 #2 失效门捆绑, 否则放量=放更多坏单。

### 问题 #9 [P1-放量] VWAP 门 0.3% 容差拦掉 40% 本可触发单

**现状**: `entry_vwap_gate_tolerance=0.003` (`unified_config.yaml:1181,1250`)。229/576=40% 的"已入带"尝试在此被拦, 是触发率仅 7% 的最大单一贡献者。0.3% 低于 1 分钟 K 线噪声底。

- 方案 A: 容差 0.3%→0.8–1.0% (保持 `entry_vwap_gate_enabled=true`, 仍拦>1%偏离)。预期恢复 150+ 成交/样本期。
- 方案 B: SIM 专用开关 `entry_vwap_gate_sim_only` 直接关闭 SIM 的 VWAP 门 (更激进, 采集"逆VWAP侧"对照数据)。
- 方案 C: 不动 — VWAP 逆侧是已知亏损入场。
- 倾向: 方案 A (贴合噪声底, 保留方向一致性过滤); 方案 B 留待 #12 gate-cost 报告量化后再定。

### 问题 #10 [P2-放量] 名义额度/持仓数上限虽非约束, 是否随放量同步上调

**现状**: notional cap 0.80 仅用 47%, max_daily_positions 30 仅用 34%。当前非约束, 但 #7+#8+#9 放量后可能触顶。

- 方案 A: 预防性上调 `max_daily_positions` 30→50, notional cap 0.80→0.90, 防止放量后被这两道"休眠闸门"反噬。
- 方案 B: 不动 — 等真触顶再调 (YAGNI)。
- 倾向: 方案 B, 但辩论需确认放量后的峰值估算 (若 15 笔/天 × 4% = 60% gross, notional 0.80 仍够)。

### 问题 #11 [P1-数据质量] 未成交指令的反事实收益未回填 (最高杠杆零成本)

**现状**: 53 条活跃指令中 **21 条 (40%) 从未触发**, 结果完全缺失 = 最大选择偏差源。`playbook_instructions` 已有 `fwd_return_t1/t3/t5/intraday` 列, 但**只对已成交的填**。shadow 采集丰富 (`trigger_miss_telemetry` 990行 / `entry_timing_shadow` 576行 / `exec_gate_audit`) 但**无消费者**, 未接入 IC 学习闭环。

- 方案 A: 盘后 job 对**所有**指令 (含未触发) 用 DA 给定 entry/SL/TP 回填 `fwd_return_*`, 存为影子结果。每周凭空 +21 IC 标注点, 零新增交易。**最高杠杆的数据质量动作**。
- 方案 B: 不做 — 只靠真实成交积累。缺点: 慢, 且选择偏差 (只有"突破触发"的入场被记录, 永远学不到"不靠突破也能成"的样本) 不消除。
- 倾向: 方案 A (与放量正交, 应无条件做)。
- **关联 #8/#9**: 若 A 落地, #8/#9 放量的边际价值下降 (影子数据已替代部分真实量) → 辩论应先评估 A 能贡献多少有效样本, 再决定放量激进度。

### 问题 #12 [P2-数据质量] 缺 gate-cost 归因, 放量决策靠猜

**现状**: 现有 telemetry 足以量化"每道门拦掉的单若成交, 反事实 PnL 多少", 但无脚本产出该报告。放宽 #8/#9 的激进度目前只能拍脑袋。

- 方案 A: 写一次性脚本 `scripts/gate_cost_report.py`, 读 `trigger_miss_telemetry.jsonl` + `entry_timing_shadow.jsonl` + 已平仓 `trade_records`, 估算"VWAP 门 0.3%→1.0% 本可多产 ~$X edge"。用真实数字驱动 #8/#9/#10 的参数选择。
- 方案 B: 不做, 凭经验直接调参 + 事后观察。
- 倾向: 方案 A 先行 (轻量、一次性), 为 #8/#9 提供量化依据; 属"决策工具"而非管线改动。

### 关于"更多交易 = 更好数据"是否成立 (辩论须正视)

- **成立的部分**: 更多成交 → 更多 IC 估计样本 → 更快毕业。当前"干净窗口 (≥07-11) 近 0 样本" (handoff.md:116) 是真问题, 放量必要。
- **关键 caveat**: 系统"持到收盘胜率 50.8%" → **入场质量已是抛硬币**。同 regime 放量只增硬币样本 (利于 IC 估计), **不改善 edge**; edge 问题在退出端。**放量是 IC 估计的必要条件, 但退出才是毕业(45%WR+正PnL)的充分条件**。
- **辩论须裁决**: 放量优先 (更快确认"退出是瓶颈") vs 先修退出再放量 (避免积累一堆低质硬币样本)。建议 #11(影子回填) 无条件先做, #7–#9(放量) 与退出侧修复并行, 不互斥。

## 关键分歧 (待辩论 agent 裁决)

1. **#2 盘中失效检测的形态**: 确定性失效门 (A) vs LLM复核 (B) vs 收紧时间窗 (C)?
   - A 观点: 确定性、可复现、不违背"运行时零LLM"。
   - B 观点: 只有 LLM 能判"新闻是否反转 thesis", 门规则抓不住语义反转。
   - C 观点: 最简单, 老指令本就该失效。
   - 可验证方式: 用 thesis_recheck shadow (已有 flag) 采集"触发时 vs 收盘"的方向一致性, 对比门/LLM 各能拦下多少亏损单。

2. **#1 告警的触发边界**: "当天应有 bridge" 如何定义 (是否所有交易日都强制要求 bridge)? IC 封锁期 LIVE=0 时, bridge 缺失是否仍需告警?
   - 可验证方式: 检查 Hermes cron 的实际产出频率与失败历史。

3. **P2 类 (#3/#4/#5) 是上线前做还是样本期偿还?** — 与前两轮 P2/P3 "post-launch偿还" 节奏是否一致?

4. **放量激进度 (#7–#9)**: 先量化 (#12 gate-cost 报告) 再调参, 还是直接小步放宽 + 事后观察?
   - 保守观点: 无量化依据直接放宽入场带/VWAP = 拍脑袋, 可能积累一堆逆VWAP亏损硬币样本。
   - 激进观点: 样本积累有时间压力 (干净窗口近0样本), 小步放宽 + telemetry 事后校准即可, 不必等脚本。
   - 可验证方式: #12 脚本产出"每道门反事实 PnL", 若 VWAP 逆侧样本历史为负则否决 #9-B。

5. **放量 vs 修退出的优先级 (核心)**: 入场质量已是抛硬币 (持收盘 50.8%), 放量只增硬币样本不改 edge。
   - 观点 A: 放量优先 — 更快用样本确认"退出才是瓶颈", 且 #11 影子回填零成本先行。
   - 观点 B: 先修退出再放量 — 否则积累的都是低质样本, 毕业(45%WR+正PnL)仍无望。
