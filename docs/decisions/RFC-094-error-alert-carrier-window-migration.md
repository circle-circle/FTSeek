- **日期**: 2026-09-22
- **类型**: L4 (载体/调度面变更; **判据零变更**, 一次一个变量)
- **触发**: 窗1 首考报告 (job `0cb47309cc88`, 2026-09-21) 提出"窗2/3/4 可迁 + 窗2 起可逐窗撤 crontab 行"。
  用户 2026-09-22 令「按建议做」= 采纳本 agent 的修正版建议 (先迁事故窗, 不撤兜底)。
- **本批性质**: 纯增量。crontab 四行**一行未动** ⇒ 即使 Hermes 侧全死, 覆盖与告警行为与变更前逐字相同。

## 1. 为什么顺序是「窗3/窗4 先, 窗2 最后」(与首考报告的差异)

首考报告建议"窗2 起"。本批改为**先迁盘前/盘后两窗 (窗3/窗4)**, 依据三条实测:

1. **事故形状只在这两窗**: INCIDENT-001 (2026-09-19, P1) = 延长时段退出链每分钟崩、连崩 7 轮
   (9/18 09:38-09:44 next_open 窗 + 16:32-16:38 盘后窗) **零告警**。补窗批 (`*/15 16-20` / `*/15 5-8`)
   正是为堵它; 窗1/2 (ET 09:00-17:45) 的历史故障面已有别的探测网。
2. **这两窗没有第二层覆盖**: 唯一窗口级心跳 `scripts/business_heartbeat.sh` 只挂
   `*/30 21-23 * * 1-5` 与 `*/30 0-5 * * 2-6` (= 窗1/2)。窗3/4 除 error_alert 本身外无兜底。
3. **窗2 边际价值最低**: 与已迁的窗1 同属盘中、同有 heartbeat 覆盖、判别形状相同
   (首考已证明"每 15min 静默成功"这一形态可用)。

## 3. 「撤 crontab 行」条件门 (预注册, 防顺手撤)

**本批不撤任何 crontab 行。** 撤行需**单独一裁**, 且同时满足:

1. 该窗 Hermes 载体**并行运行 ≥14 天** (含至少 1 个周六凌晨段 = 窗4 的 `2-6` dow 形状,
   与至少 1 次 gateway 重启后的派发恢复观察);
2. 期内 `/opt/ftseek/FTSeek-US/scripts/data_freshness_watchdog.py` (crontab `25 6 * * 2-6`) 的
   **D2「应跑未跑」零缺席**, D3「最新一条 failed」零告警;
3. 用户**显式接受**撤行后的降级: gateway/派发面死掉时, 该窗的 ERROR 告警将**静默至次日 06:25**
   (届时唯一外部探测器才报)。即盲窗从 15min 放大到 ≤24h。

理由 (写进本 RFC 以备后人复核): 这条链存在的全部理由就是 **15min 内**发现故障
(INCIDENT-001 的病灶正是"连崩 7 轮零告警"); Hermes 载体**无法给自己的死亡报警**, 故
crontab 同窗行不是冗余重复而是该盲窗的**唯一探测器**。并行代价≈0 (子进程 0.2-1.0s,
`data/.alert_state` 跨进程共享 ⇒ 不双推), 撤行收益≈0 ⇒ 收益/风险严重不对称。

**守卫成本 (实测, 避免误传成"撤行有守卫成本")**: `docs/references/crontab-loop-baseline.txt`
无 error_alert 行, `tests/test_control_loop_ledger.py` 无 crontab-* 行反查 ⇒ 撤行不触任何守卫,
只影响台账口径 (L4 级)。故"不撤"是**风险判断, 不是守卫强制**。

## 5. 失效模式 (与窗1 同族)

- gateway/派发面死 ⇒ Hermes 侧静默 (crontab 同窗行兜底; 次日 06:25 watchdog D2/D3 事后报);
- 冬令时 (2026-11-01 起) CST 相对 ET 右移 1h ⇒ 四个窗的 CST 表达式需重评 (与 crontab 四行同批);
- 线上副本 vs 仓内漂移 → `tests/test_ops_scripts_sync.py` 红;
- 阈值/判据被改而载体未对齐 → 台账 §6.2 判据同源纪律 (`error_alert.py::LEVEL_MARKERS`)。
