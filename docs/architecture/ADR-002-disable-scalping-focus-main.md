# ADR-002: 暂停 Scalping, 聚焦主线策略

**状态**: 已批准  
**日期**: 2026-05-31  
**决策者**: 项目负责人 + Claude  

## 背景

FTSeek-US 系统当前采用双线架构:
- **主线 (Main Pipeline)**: 趋势跟踪策略, 持仓 2h-6h, 以 SHORT 为主
- **日内短线 (Scalping)**: 均值回归策略, 持仓 <30min, 双向交易

经过全链路审计和历史数据分析, 发现 scalping 持续表现不佳, 且双线架构带来显著的运维复杂度和风险冲突。

## 数据依据

### 交易表现对比 (2026-04-24 至 2026-05-30)

| 指标 | 主线 | Scalping |
|------|------|----------|
| 交易数 | 169 | 150 |
| **胜率** | **36.7%** | **18.0%** |
| 总 PnL | -$12,939* | -$1,638 |
| 平均单笔 | -$76.56 | -$10.92 |
| 平均持仓 | 1.5h | <30min |
| 止损触发率 | 35% | **82%** |

*主线亏损主要来自 SHORT_PROXY_OPTION 灾难 (13笔期权 -$30K), 剥除后主线股票交易 +$17,298

### 主线核心优势

```
SHORT + TRAILING_STOP 组合:
- 84 笔交易
- 42.9% 胜率
- +$13,054 总收益
- 这是系统唯一被验证的 alpha 来源
```

### Scalping 致命问题

1. **82% 交易以止损退出** - SL 在盈利前就被打掉
2. **90% 持仓 <30min** - 价格没机会走到 TP
3. **LONG 方向 6.5% 胜率** - 均值回归做多完全失效
4. **150 笔样本足够大** - 不是运气问题, 是策略-市场匹配问题

## 架构冲突分析

### 已发现的冲突 (全链路审计)

| # | 级别 | 问题 | 影响 |
|---|------|------|------|
| C1 | 🔴 | ExitRuleDispatcher 未过滤 scalping | 双重平仓风险 |
| C2 | 🔴 | PositionStore 同标的覆盖 | 数据丢失 |
| C3 | 🔴 | 三套资金系统互不通信 | 资金分裂 |
| C4 | 🔴 | 日回撤两个独立池 (3%+2%=5%) | 风控漏洞 |
| H1-H8 | 🟠 | 风控/退出/同步缺口 | 运维复杂度 |

### 运维成本

- **代码复杂度**: 双重退出路径、双重资金追踪、双重风控检查
- **调试难度**: 需要同时追踪两条线的状态和交互
- **测试覆盖**: 需要验证所有交叉场景 (同标的/同时段/反向持仓)
- **配置管理**: 两套独立参数, 容易不一致

## 决策

**暂停 scalping, 聚焦主线已验证的 edge**

### 立即执行

```yaml
# config/unified_config.yaml
strategies:
  main:
    capital_pct: 0.80    # 从 0.65 → 0.80 (收回 scalping 15%)
  scalping:
    capital_pct: 0.0     # 从 0.15 → 0.0
    enabled: false       # 从 true → false
```

### 代码处理

- **ScalpingEngine 保留**, 不删除任何代码
- 退出路径、风控逻辑、数据采集全部保留
- 后续可通过 `enabled: true` 随时恢复
- 所有 C1-C4 + H1-H8 冲突自动消除 (scalping 不运行)

### 资金重新分配

```
修改前:
  main: 0.65 (81.25%)
  scalping: 0.15 (18.75%)
  总计: 0.80

修改后:
  main: 0.80 (100%)
  scalping: 0.0 (0%)
  总计: 0.80
```

主线可用资金 **+23%** (0.65 → 0.80)

## 预期效果

### 正面影响

1. **消除所有双线冲突** - C1-C4 + H1-H8 不再触发
2. **运维复杂度大幅降低** - 单线路径, 易于调试和测试
3. **资金效率提升** - 15% 资金从负收益策略转移到正收益策略
4. **聚焦已验证 edge** - SHORT + trailing stop 是系统唯一 alpha 来源
5. **风险控制** - 单一日回撤池 3%, 不再有 5% 漏洞

### 潜在风险

1. **交易频率下降** - scalping 贡献 150 笔交易 (47% 的总交易量)
2. **数据采集减少** - 失去高频交易的微观结构数据
3. **策略多样性降低** - 只剩趋势跟踪, 震荡日无策略覆盖

### 风险缓解

1. **交易质量 > 数量** - 主线 36.7% WR vs scalping 18% WR, 质量显著提升
2. **主线可扩展** - 增加趋势跟踪的标的池或降低入场门槛
3. **代码保留** - scalping 基础设施完整, 后续可重新启用

## 替代方案评估

### 方案 A: 缩减为最小可行版 (未选)

保留 scalping 但大幅缩减:
- 仅 SHORT 方向
- 仅震荡日触发
- 资金降至 5%

**未选原因**: 18% WR 的根本问题未解决, 5% 资金仍会持续失血

### 方案 B: 保留双线继续优化 (未选)

投入更多时间调参和修复架构问题

**未选原因**: 
- 150 笔样本已足够, 继续优化边际收益低
- 架构修复 (C1-C4) 需要大量工程投入
- 机会成本高, 不如聚焦主线

### 方案 C: 暂停 scalping, 聚焦主线 (已选)

**选择原因**:
- 数据明确支持主线 SHORT+trailing edge
- 消除所有双线冲突和运维负担
- 代码保留, 后续可恢复
- 符合"简单优先"的治理原则

## 后续计划

### 短期 (1-2 周)

1. 监控主线表现, 确认资金效率提升
2. 观察交易频率是否过低, 必要时扩展主线标的池
3. 验证所有双线冲突不再触发

### 中期 (1-3 个月)

1. 持续积累主线交易数据
2. 分析 scalping 失败的根本原因 (策略-市场匹配? 参数? 执行?)
3. 如果发现可行的短期策略机会, 重新评估是否启用

### 长期 (3-6 个月)

1. 如果主线表现稳定, 考虑是否需要策略多样性
2. 如果重新启用 scalping, 必须先解决:
   - 策略-市场匹配验证 (回测 + 模拟盘)
   - 架构冲突修复 (C1-C4)
   - 小规模试点 (5% 资金)

## 监控指标

### 关键指标

- **主线胜率**: 目标 ≥ 40% (当前 36.7%)
- **主线日均收益**: 目标 ≥ $500 (当前 -$2,187, 剥除期权后 +$576)
- **交易频率**: 观察是否过低 (<5笔/日)
- **最大回撤**: 目标 ≤ 5% (当前 3% 限制)

### 告警阈值

- 主线胜率 < 30% → 重新评估策略
- 日均交易 < 3 笔 → 考虑扩展标的池
- 连续 5 日亏损 → 触发熔断审查

## 回滚方案

如果决策错误, 可立即回滚:

```bash
# 修改 config/unified_config.yaml
strategies:
  main:
    capital_pct: 0.65
  scalping:
    capital_pct: 0.15
    enabled: true

# 重启服务
systemctl restart ftseek-us
```

回滚时间: < 5 分钟
